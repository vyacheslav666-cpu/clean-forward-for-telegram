# Changelog

Все заметные изменения проекта документируются в этом файле. Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), а версии следуют [Semantic Versioning](https://semver.org/lang/ru/).

## [Unreleased]

### Added

- `src/telegram/domContract.ts` — единственное место, где объявлены селекторы Telegram Web K.
  Раньше они дублировались по двенадцати адаптерам: `.popup-send-photo.popup-new-media.active`
  жил в четырёх файлах, строка активной строки диалога — в трёх;
- `contracts/tweb-dom-contract.json` — инвентарь из 102 токенов (класс/id/атрибут/элемент) со
  статусом: `required` (обязан быть в апстриме), `legacy` (оставлен для старых сборок),
  `dynamic` (Web K собирает имя в рантайме, поиск по литералу ничего не доказывает);
- `npm run check:tweb` (`scripts/check-tweb-contract.mjs`) — скачивает исходники
  `morethanwords/tweb` и проверяет, что каждый `required`-токен там ещё существует. Отдельный
  workflow `Telegram DOM contract`: еженедельно и на PR, меняющих сам контракт. В `validate` не
  входит — он не должен зависеть от сети и чужого репозитория;
- `tests/telegram/dom-contract.test.ts` — селектор, написанный прямо в адаптере, роняет suite,
  если его токены не объявлены в контракте. Без этого проверку апстрима можно было бы обойти,
  просто не записав селектор.

### Fixed

- **панель реакций уезжала в текст отправляемого сообщения.** Пересланный пост канала получал
  хвост из эмодзи реакций и их счётчиков (`✦ ✦ ✦ … 1 1.28K 746`). Причина: Web K кладёт
  `<reactions-element>` **внутрь** `div.message` (`bubbles.ts`, `messageDiv.append(reactionsElement)`),
  а чтение текста исключало только `.time` и `.clearfix`. Хуже того, при наличии реакций Web K
  переносит `.time` внутрь панели, поэтому счётчики оказывались единственным, что оставалось от
  всего блока;
- вместе с реакциями из читаемого текста ушли остальные части `.message`, которые Web K сам не
  считает текстом сообщения: превью ссылки (`.webpage`), заголовок блока кода с кнопкой Copy
  (`.code-header`), цитата ответа (`.reply`) и блок проверки фактов (`.bubble-fact-check`).
  Список взят из апстрима: `BUBBLE_TEXT_HIGHLIGHT_SKIP` в `components/chat/bubbles.ts` — это
  собственный ответ Web K на тот же вопрос;
- захват и подтверждение доставки больше не могут разъехаться: оба читали `.message` со своим
  локальным списком исключений, теперь оба используют `MESSAGE_TEXT_IGNORED_SELECTORS` из
  `domContract.ts`. Разъезд был не теоретическим — сообщение, получившее реакцию между Send и
  подтверждением, сравнивалось неравным и останавливало batch как `unknown`.

### Changed

- сверка с апстримом нашла два устаревших комментария в коде. `.btn-menu-overlay` помечался как
  «удалён из текущего Web K», хотя он по-прежнему создаётся — только не внутри меню, а
  document-level обработчиком (`helpers/overlayClickHandler.ts`). И наоборот: `.render-progress`
  в апстриме больше не существует (`RenderProgressCircle` рисует div без класса), то есть
  готовность upload preview фактически держится на одном `.preloader`. Поведение не менялось,
  оба факта записаны в контракт.

## [0.1.11] - 2026-08-19

### Fixed

- проверка «Telegram сейчас что-то отправляет» снова работает в навигаторе и в очистке upload
  preview. Обе искали класс `.sending`, которого текущий Web K не ставит, поэтому обе молча не
  срабатывали никогда: навигация к получателю не ждала чужую отправку, а закрытие preview не
  замечало, что оно что-то отправило. Состояние читается тем же способом, что и подтверждение
  отправки, — по `is-sending`/`is-outgoing` и временному дробному `data-mid`; `.sending` оставлен
  для старых сборок Web K;
- восстановление исходного чата больше не может быть заблокировано навсегда. Сообщение, зависшее
  в отправке с офлайн-сессии, остаётся in-flight бесконечно, поэтому проверка «в чате идёт
  отправка» никогда бы не разблокировалась, а неудачное восстановление — это отказ безопасности
  всего batch. Учитывается только отправка, начавшаяся после снимка состояния, а для
  `source-restore` проверка не применяется вовсе: восстановление ничего не отправляет.

### Added

- `OutgoingInFlightBaseline` и `findOutgoingInFlight()` в `src/telegram/outgoingMessageState.ts`:
  снимок уже идущих отправок и поиск незавершённых по области DOM. Отклонённая отправка (`is-error`)
  в результат не попадает — Telegram её уже остановил, ждать нечего;
- `tests/telegram/outgoing-message-state.test.ts`, сценарии очистки preview в `composer.test.ts`
  (закрытие preview начало отправку в чате получателя — отказ; отправка, шедшая до закрытия, —
  не в счёт) и новые сценарии в `navigation.test.ts`:
  зависшее сообщение не блокирует, отправка после снимка блокирует, отклонённая игнорируется,
  восстановление источника не блокируется, временный id переживает перерисовку бабла.

## [0.1.10] - 2026-08-18

### Fixed

- захват видео больше не оставляет копию файла в хранилище самого Telegram и не может довести
  origin до исчерпания квоты. Чтобы собрать полные байты, userscript читает файл через service
  worker Web K, а тот сохраняет **каждый** выданный чанк в CacheStorage `cachedStreamChunks` и
  дополнительно читает 20 МБ вперёд (`src/lib/serviceWorker/stream.ts`). Это тот же origin, где
  Telegram держит собственную сессию и state, поэтому переполнение бьёт по Telegram, а не по
  userscript. Теперь перед чтением проверяется свободное место (захват отклоняется, если копия в
  него не помещается), а после чтения из кэша удаляются ровно те чанки, которые вызвал захват.

  Проверено по исходному коду Telegram Web K. Связь с белым экраном Web K у пользователя **не
  доказана** — это устранение подтверждённого побочного эффекта, а не подтверждённая причина.

## [0.1.9] - 2026-08-18

### Added

- **видео можно переслать как новое сообщение.** Раньше видео отклонялось до recipient picker:
  delivery strategy для `role: "video"` существовала и была покрыта тестами, но production capture
  умел читать из DOM только фото. Теперь одно обычное видео читается из бабла целиком — размеры и
  длительность берутся у загруженного `<video>`, подпись сохраняется;
- сборка полных байтов медиа. Telegram отдаёт видео своим service worker, который на любой запрос
  отвечает `206 Partial Content` и без заголовка `Range` возвращает только первый чанк. Обычный
  `fetch` дал бы усечённый файл, который остаётся воспроизводимым видео и молча заменил бы
  оригинал, поэтому байты собираются по диапазонам, а полнота подтверждается общим размером из
  `Content-Range`. Неизвестный общий размер, обрыв передачи и превышение лимита захвата
  отклоняются;
- `tests/telegram/video-capture.test.ts` и `tests/telegram/video-snapshot.test.ts`: сборка файла из
  нескольких чанков, отказ при неизвестном размере и при обрыве, проверка лимита до скачивания,
  чтение размеров и длительности, отказ для видео-кружка и GIF, отказ до загрузки metadata и
  полный путь через `SourceCaptureService`.

### Fixed

- **сообщения приходили получателю в перепутанном порядке.** Подтверждением отправки считался
  optimistic бабл Web K, который появляется сразу после нажатия Send, ещё до ответа сервера.
  Причина — проверка «сообщение ещё отправляется» искала класс `sending`, которого текущий Web K
  не ставит: он помечает бабл `is-outgoing` и `is-sending` и держит временный дробный `data-mid`
  (`serverId + 0.0001`), пока сервер не выдаст настоящий id. Из-за этого следующий item уходил в
  чат, пока предыдущий ещё загружался, и Telegram нумеровал сообщения по скорости upload, а не по
  порядку bundle — что и было видно на двух картинках разного размера. Теперь отправка считается
  завершённой только по серверной identity: временный mid и классы отправки должны исчезнуть.
  Контракт сверен с исходным кодом Telegram Web K (`bubbles.ts`, `appMessagesIdsManager.ts`);
- отправка большого файла больше не превращается в `unknown` по таймауту. Ожидание подтверждения
  теперь различает «ничего не происходит» (прежние 12 s плюс bounded reconciliation) и «Telegram
  наблюдаемо продолжает отправку» — во втором случае ожидание длится до 5 минут, потому что
  upload файла предельного размера легко переживает 12 s. Зависшая отправка по-прежнему
  заканчивается bounded `unknown`;
- Telegram-отказ уже принятого сообщения (`is-error`) распознаётся сразу и останавливает batch с
  явной причиной вместо ожидания полного таймаута;
- видео с подписью ушло бы одной подписью без видео: текстовый adapter объявлял, что поддерживает
  любое сообщение без картинок, и перехватывал media-бабл раньше binary adapter. Найдено тестом
  сквозного пути, а не в production.

### Changed

- video note (кружок) и GIF/animation намеренно не считаются видео: повторная отправка через media
  path изменила бы смысл сообщения, поэтому они остаются unsupported, а не отправляются как
  «похожий» тип;
- capture видео не начинается, пока браузер не сообщил его реальные размеры и длительность. Иначе
  Telegram строил бы upload по выдуманным значениям, поэтому сообщение отклоняется до picker.

## [0.1.8] - 2026-08-17

Контракт сверен с исходным кодом Telegram Web K и с поведением реального Chrome, а не с записями
ручного исследования.

### Fixed

- «Telegram не завершил обработку подписи» возникало на **любом многострочном** тексте и подписи.
  Причина не в Telegram: Chrome записывает результат `execCommand("insertText")` как отдельные
  блоки `<div>` на строку, а `readTelegramText` знал только `<br>` и молча терял каждый перенос.
  Проверка «вставленное совпадает с подготовленным» поэтому никогда не выполнялась, ожидание
  упиралось в 2 секунды и падало. Сам Telegram читает такие блоки корректно
  (`BLOCK_TAGS` в `getRichElementValue.ts`), то есть отправленное сообщение было бы правильным —
  fail-closed срабатывал на ложном несовпадении и блокировал корректную отправку;
- та же проверка используется до Send, при очистке подготовленного текста и при восстановлении
  пользовательского draft, поэтому многострочный draft в чате получателя мог привести к
  safety stop «Recipient draft restoration could not be confirmed»;
- `readTelegramText` теперь считает границей строки те же block-теги, что и Telegram, и отбрасывает
  только замыкающий filler Chrome, не трогая настоящую пустую строку;
- ошибка предыдущей попытки оставалась на панели во время следующей: под строкой со статусом
  «Подготавливаем» висел красный текст при счётчиках 0/0/0, и успешный retry выглядел как отказ.
  Начало новой попытки очищает `detail`; `retryReason` сохраняется как история попыток;
- проверка стабильности подписи искала `.animating` по всему popup и могла упереться в постороннюю
  анимацию Telegram. Web K ставит `is-changing-height` и `animating` на само поле подписи
  (`SetTransition` в `inputFieldAnimated.ts`), поэтому проверка ограничена этим полем;
- отказ подписи больше не сводится к одному непрозрачному сообщению: разделены «значение не
  совпало» и «поле ещё анимируется», для несовпадения указываются длина, число строк и позиция
  первого расхождения. Сам текст подписи в сообщение не попадает.

### Changed

- мок `document.execCommand` в тестах воспроизводит реальную разметку Chrome вместо плоского
  `textContent`. Прежний мок делал round-trip успешным в jsdom при полностью сломанном production:
  383 зелёных теста не ловили дефект, а один тест прямо фиксировал сломанное поведение как
  ожидаемое;
- `docs/delivery-pipeline-audit.md` приведён в соответствие с кодом: пункты P1 10–12 (draft
  preservation, source chat restoration, automatic retry) реализованы, соответствующие строки
  target state machine заполнены. Добавлен раздел о новом классе дефекта — предположении о
  поведении браузера, а не Telegram.

### Added

- `tests/telegram/read-telegram-text.test.ts` на фикстурах, снятых с реального вывода Chrome:
  две и три строки, пустая строка между строками, кириллица, emoji в `img[alt]`, `<br>` из bubble,
  blockquote, замыкающий filler и `ignoredSelectors`;
- `tests/delivery/delivery-batch-attempts.test.ts` — очистка ошибки предыдущей попытки при старте
  новой, сохранение терминального отказа и неприкосновенность подтверждённого unit при retry
  следующего;
- `tests/telegram/upload-preview-caption.test.ts` — посторонняя анимация в popup не мешает,
  анимация самого поля учитывается, и несовпадение значения называется без раскрытия подписи.

## [0.1.7] - 2026-08-17

### Fixed

- «Остановка безопасности: Prepared content cleanup could not be confirmed» больше не скрывает
  причину. Исходное сообщение о том, что именно не удалось подготовить, затиралось сообщением об
  уборке, и на панели оставался отказ без причины. Теперь показываются обе части;
- уборка preview имела пять независимых условий отказа и один общий `false`, поэтому определить
  причину по интерфейсу было невозможно. Каждое условие теперь называет себя;
- проверка «после закрытия preview ничего не отправляется» искала `.sending` по всему документу и
  срабатывала на посторонних исходящих сообщениях в других чатах. Проверка ограничена чатом
  получателя.

## [0.1.6] - 2026-08-17

### Fixed

- отправка картинки часто падала с «Telegram не открыл меню вложений»: ожидание было 2 секунды,
  но Telegram строит это меню только после сетевого запроса списка attach-ботов. Лимит поднят
  до 10 секунд;
- после такого отказа меню вложений оставалось открытым поверх чата и выглядело как намертво
  зависший Telegram. Причина та же, что и у контекстного меню: закрытие опиралось на
  несуществующий `.btn-menu-overlay`. Теперь меню закрывается нативно — повторным нажатием на ту
  же кнопку вложений, и закрытие отслеживается ещё две секунды на случай, когда меню
  открывается уже после отказа;
- кнопка вложений ищется по самому элементу `attach-menu-button`, без класса `attach-file`,
  который Web K больше не проставляет. Старая разметка продолжает поддерживаться.

### Added

- прямые тесты `MediaModeActivator`, у которого до этого не было ни одного собственного теста:
  он был полностью замокан в тестах composer, поэтому ни таймаут, ни оставшееся открытым меню
  не были заметны.

## [0.1.5] - 2026-08-17

Селекторы сверены с исходным кодом Telegram Web K, а не с записями ручного исследования.

### Fixed

- пункт контекстного меню не появлялся **никогда на мобильных и никогда в режиме выделения**:
  требовался селектор `.btn-menu.contextmenu.active.has-items-wrapper .btn-menu-items`, но Web K
  переносит пункты в эту обёртку только когда к меню прикреплена панель реакций, а это бывает
  лишь на десктопе и никогда при выделении. Теперь контейнером считается сама `.btn-menu`, а
  обёртка используется, если она есть;
- закрытие меню опиралось на соседний элемент `.btn-menu-overlay`, которого в текущем Web K нет —
  меню закрывается снятием класса `active` через общий обработчик. Добавлен тот же путь закрытия
  с сохранением совместимости со старой разметкой;
- кнопка в панели выделения вставлялась внутрь слота нативного Forward, а `ChatInputPlate`
  резервирует в боковом слоте место ровно под одну иконку, из-за чего кнопку зажимало. Теперь
  действие получает собственный слот `chat-input-plate-side`, который удаляется вместе с ним;
- на Apple-тач Web K открывает меню собственным long-tap таймером и не отправляет `contextmenu`,
  поэтому исходное сообщение не запоминалось. Добавлено отслеживание нажатия для touch и pen;
  для мыши поведение не изменилось.

## [0.1.4] - 2026-08-17

### Fixed

- Telegram Web K больше не зависает при загрузке: общий MutationObserver вызывал разрешение
  composer на каждой пачке мутаций, а оно доходило до `getComputedStyle` и форсировало
  синхронный пересчёт стилей всего приложения. Теперь дешёвые признаки selection mode
  проверяются первыми, и вне выделения обработка мутации не вызывает reflow;
- действие в нативном selection toolbar снова видно: shallow clone нативной кнопки Forward не
  копировал её иконку-потомка, поэтому в панели была пустая кнопка без иконки и текста.

### Added

- пункт «Отправить как новые» в нативном контекстном меню selection mode: он работает над всем
  выбранным набором, как и соседний `Forward selected`, а не над одним долгонажатым сообщением;
- поддержка обоих якорей меню (`Forward` и `Forward selected`) и переименование пункта при
  переиспользовании одного и того же меню Telegram между обычным режимом и selection mode;
- разрешение selection context при скрытом Telegram message input: в selection mode ввод
  скрывается плитой выделения, поэтому read-only поиск источника больше не требует его видимости.
  Все пути, которые пишут в composer, сохраняют строгую проверку видимости.

## [0.1.0] - 2026-08-04

### Added

- подготовка обычного текста как нового сообщения;
- подготовка одной фотографии с необязательной подписью;
- собственный выбор одного получателя из загруженных диалогов;
- multi-select UI без навигации, массовой подготовки или отправки для нескольких отмеченных строк;
- ручное подтверждение отправки через интерфейс Telegram Web K;
- автоматические тесты доменной логики, DOM-интеграции и single-recipient flow;
- production-сборка Tampermonkey userscript;
- документация по архитектуре, приватности и ограничениям.

### Security

- содержимое переноса хранится только в памяти;
