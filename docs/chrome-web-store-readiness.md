# Готовность к публикации в Chrome Web Store

Статус: **не готово к отправке.** Оценка от 2026-08-27 по состоянию `7920176`.

Хорошая новость сразу: сам код к ревью претензий почти не вызовет. Проверено — ни `eval`,
ни `new Function`, ни `innerHTML`, ни динамического `import()`; сборка не минифицируется
([vite.config.ts:96](../vite.config.ts:96)), то есть под правило про обфускацию не попадает;
`chrome.*` API не используются вообще; ни `localStorage`, ни IndexedDB; единственные `fetch` —
за `blob:`/же-origin байтами медиа самого Telegram. Ни одного разрешения в манифесте.

Блокеры лежат не в коде, а в политике, брендинге и раскрытии данных.

---

## 1. Блокеры — без них отклонят

### 1.1 Нет privacy policy

Расширение читает содержимое личных переписок. Для Chrome Web Store это `Personal
communications` — одна из категорий, которые обязательно раскрываются в форме **Privacy
practices**, и при любом сборе данных требуется **опубликованный URL** политики
конфиденциальности. Файла нет ни в репозитории, ни где-либо ещё.

То, что данные живут только в памяти и никуда не уходят, — не освобождение, а **содержание**
политики. Её надо написать и опубликовать (GitHub Pages подойдёт), а в форме заполнить:

- какие категории данных затрагиваются (`Personal communications`);
- что данные не покидают устройство, не передаются третьим лицам, не продаются, не
  используются для оценки кредитоспособности;
- три обязательных чекбокса-декларации в конце формы.

### 1.2 Название содержит «Telegram»

Политика **Impersonation and Intellectual Property**. Формула «X for Telegram» обычно проходит,
но не сама по себе. Нужно:

- дисклеймер в описании листинга и в README: не аффилировано с Telegram, не одобрено Telegram;
- не использовать логотип Telegram нигде — ни в иконке, ни в скриншотах, ни в promo tile;
- перепроверить актуальные brand guidelines Telegram перед отправкой.

### 1.3 Иконка: фирменный синий Telegram заменён — снято

[assets/icon-128.png](../assets/icon-128.png) — белая стрелка в тёмно-синем круге `#3A4555`.
Прежняя иконка была той же стрелкой в круге фирменного синего Telegram, и это давало риск
формулировки «confusingly similar to another product». Расцветка уведена от узнаваемой —
риск снят.

Мастер иконки (1254×1254) в репозитории не лежит, в `assets/` только уменьшенная до 128×128.
Для §3.2 исходник придётся искать заново — его стоит положить рядом.

### 1.4 `world: "MAIN"` потребует защиты

[vite.config.ts:66](../vite.config.ts:66). Технически легально в MV3 и обосновано по существу:
альбомный bridge читает `apiManagerProxy` с глобала страницы, в изолированном мире его не
видно. Но для ревьюера content script в MAIN world — это полный доступ к странице, включая
приватные объекты Telegram, и это самая вероятная причина ручного разбора и задержки.

Обоснование уже написано в комментарии к плагину — его надо перенести в поле justification
дословно и человеческим языком, а не отправлять пустым.

### 1.5 Версия в манифесте отстаёт от `package.json`

`package.json` — `0.1.12`, `dist/manifest.json` — `0.1.11`: `dist/` собран из более старого
состояния. Отправка в стор пакета с неверной версией — мусор в публичной истории, который
нельзя переписать. Сборка обязана падать при расхождении, а не совпадать по удаче (см. 3.1).

### 1.6 Продукт снимает атрибуцию — это надо назвать прямо

Смысл расширения — отправить чужое сообщение без пометки `Forwarded from`. Ревьюер может
прочитать это как обход механизма платформы. Скрывать назначение нельзя: политика требует,
чтобы описание точно отражало поведение, а несоответствие — отдельное основание для снятия.

Честная формулировка сильнее уклончивой: пользователь вручную выбирает свои сообщения,
вручную выбирает получателей, содержимое пересоздаётся через штатный интерфейс отправки,
никакой автоматизации без явного действия пользователя нет. Это и стоит написать.

## 3. Разработать

### 3.1 Проверка сборки в `validate`

Сейчас `npm run validate` не смотрит на `dist/` вообще, и тестов на манифест нет ни одного.
Добавить проверку, которая падает, если:

- версия в `manifest.json` не равна версии в `package.json`;
- манифест не парсится или не проходит схему MV3;
- в `dist/` нет всех файлов расширения;
- в собранном бандле встретились `eval(`, `new Function(`, `innerHTML =` — регрессия, которая
  превращает чистое ревью в разбирательство.

### 3.2 Полный набор иконок

Есть только `128`. Нужны `16`, `32`, `48`, `128` — 16 и 32 показываются в списке расширений и
в меню, без них Chrome масштабирует 128 и выглядит это плохо.

### 3.3 Поля манифеста

Добавить `homepage_url` и `author`. Опционально `minimum_chrome_version` — `world: "MAIN"` в
`content_scripts` поддерживается с Chrome 111, и объявить это честнее, чем молча ломаться.

### 3.4 Видимый признак жизни

Единственное подтверждение, что расширение работает, — появившийся пункт в меню Telegram.
Если контракт разошёлся и пункт не вставился, пользователь не отличит «сломалось» от «не
установилось». Минимальный `action` с иконкой в тулбаре и статусом «контракт совпал / не
совпал» снимает целый класс обращений в поддержку.

### 3.5 Выключатель

Выключить расширение можно только через `chrome://extensions`. Для инструмента, который сам
жмёт Send, стоит иметь способ быстро остановить batch и отключить интеграцию из самого
интерфейса.

## 4. Протестировать

Пробелы, которые сегодня не покрыты ничем:

- **манифест и сборка** — тестов нет вовсе (см. 3.1);
- **обновление расширения на лету** — Chrome перезагружает content script, а вкладка Telegram
  остаётся старой. Что произойдёт с уже запущенным batch — не проверено;
- **две вкладки Telegram одновременно** — `claimCleanForwardRuntime` рассчитан на одиночный
  runtime, но проверено ли это на двух вкладках и двух аккаунтах;
- **удаление расширения посреди операции** — Telegram обязан остаться работоспособным;
- **обе поставки из одной сборки** — README утверждает, что код побайтово одинаков; это
  проверяемое утверждение, и его стоит проверять автоматически, а не верить;
- **packed-сборка**, а не только `Load unpacked`: в стор уезжает ZIP, и проверять надо именно
  его.

Browser E2E с авторизованной сессией в suite не входит и войти не может — это зафиксировано в
README и остаётся правдой. Значит ручной чеклист перед релизом становится обязательным
шагом, а не рекомендацией.

## 5. Задокументировать

Для листинга (ничего из этого пока нет):

- **скриншоты** — минимум один, `1280x800` или `640x400`. На них не должно быть реальных
  переписок, имён, аватаров и `peerId`. Понадобится демонстрационный аккаунт;
- **описание** — до 132 символов summary плюс полное описание с дисклеймером о
  неаффилированности и честной формулировкой назначения (см. 1.6);
- **single purpose** — одно предложение: расширение копирует выбранные сообщения Telegram
  Web K в выбранные чаты как новые;
- **обоснование host permission** `https://web.telegram.org/k/*` и `world: "MAIN"` (см. 1.4);
- **privacy policy** — отдельный файл в репозитории плюс опубликованный URL (см. 1.1).

В репозитории:

- `PRIVACY.md`;
- раздел README про установку из стора — появится после публикации;
- строка в CHANGELOG про первую публикацию.

## 6. Порядок действий

1. Закрыть 1.5 — расхождение версий, и сразу 3.1, чтобы оно не вернулось.
2. Написать `PRIVACY.md` и опубликовать URL.
3. Перерисовать иконку вне палитры Telegram, доделать 16/32/48.
4. Дописать поля манифеста (3.3).
5. Решить по п.3 аудита: чинить кастомные эмодзи или явно отклонять такие сообщения.
6. Подготовить листинг: скриншоты на демо-аккаунте, описание с дисклеймером, тексты
   обоснований.
7. Прогнать ручной чеклист из README на **packed** сборке.
8. Отправлять.

Ожидание после отправки: `world: "MAIN"` плюс тематика «личные переписки» почти наверняка
уводят заявку из автоматической проверки в ручную. Это недели, а не часы. Планировать стоит
исходя из этого, и не пытаться ускорить, урезав обоснования.
